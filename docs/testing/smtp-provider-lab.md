# SMTP provider lab evidence

The SMTP provider lab is a test-only RFC 5321 server used to exercise the real
SMTP adapters and P7 acceptance CLI over loopback or the isolated Docker E2E
networks. It requires STARTTLS and AUTH. Its TLS certificate is either a
throw-away CA/server identity generated by the local integration test or the
ephemeral test-only server identity mounted by the Docker E2E harness. The
client still performs normal certificate-chain and hostname verification.

`tests/system_e2e/smtp_provider_lab.py` exposes STARTTLS SMTP on port `1025`
at `smtp-provider` and an independent HTTP API on port `8091`. `GET /messages`
returns accepted Message-ID, subject and recipient metadata, never message
bodies. `GET /attempts` returns SMTP response-mode and acceptance metadata,
never passwords.
The control endpoints `POST /control/reset` and `POST /control/behavior` require
`X-SMTP-Lab-Control`; the token must remain test-only and must not enter
artifacts. The HTTP API must be reachable only from the isolated E2E networks.

The provider supports four DATA outcomes:

| Mode | SMTP behavior | Expected client meaning | Independent receipt |
| --- | --- | --- | --- |
| `accept` | Accept DATA and return 250 | Delivered/submission accepted | Present |
| `reject_transient` | Return 451 after DATA | Definite temporary rejection; retryable at the delivery boundary | Absent |
| `reject_permanent` | Return 550 after DATA | Definite permanent rejection | Absent |
| `accept_then_drop` | Record accepted DATA, then close before 250 | Unknown; do not resend blindly | Present |

The production acceptance CLI proof launches the lab as a separate process and
uses its real validator, provider tester, DNS lookup, STARTTLS implementation,
and AUTH client. It passes the password through the environment, applies a
per-socket timeout, writes the send evidence, and verifies the exact observed
Message-ID in a later CLI invocation. The independent API is the receipt oracle
for the simulated provider. The `run_provider_outcome_matrix` and
`verify_ambiguous_worker_delivery` helpers in
`tests/system_e2e/smtp_provider_suite.py` are designed for the registered
black-box platform-configuration journey. They drive provider validation/testing
and governed recovery through the public control-plane API, verify receipts
through the separate provider API, and prove that replaying the same issue
command after UNKNOWN does not cause another SMTP attempt. They do not import
application code or connect to PostgreSQL. The separately registered
`smtp-provider-lab` E2E suite uses that provider with the black-box runner. Its
worker path checks a governed accepted delivery against the independent
receipt API, then sends once in `accept_then_drop` mode and verifies UNKNOWN
plus idempotent replay with no second SMTP attempt. The older
`platform-configuration` suite keeps its existing Mailpit scenarios.

Run focused local evidence with:

```bash
uv run pytest tests/integration/test_smtp_provider_lab_acceptance.py \
  tests/modules/platform_configuration/test_smtp_tls_protocol.py -q
```

This proves the client’s TCP/TLS/authentication behavior and its classification
of the four deterministic provider responses. It does not prove Internet
deliverability, provider reputation or throttling policy, SPF/DKIM/DMARC,
recipient mailbox behavior, DNS behavior for a production domain, or any
production provider’s undocumented response semantics. A green lab run is not
production SMTP acceptance.
