## 1. Objetivo vigente

Request Engine es un motor multiempresa de agenda operado por agentes de IA y por un panel humano. Convex es la fuente de verdad transaccional; Chatwoot conserva conversaciones y handoff; Evolution API proporciona WhatsApp Baileys solo para pilotos; n8n es el orquestador temporal.

El MVP cubre citas con hora (`fixed_time`), ventanas por orden de llegada (`arrival_window`), clases recurrentes (`class_session`), sedes, recursos, horarios, excepciones, feriados, reservas grupales, tutores, seguros, exequátur, confirmaciones, lista de espera, onboarding conversacional, REST/OpenAPI y panel administrativo.

Fuera de alcance por ahora: pagos, reclamaciones ARS, expediente clínico, inventario, logística y calendarios externos funcionales.

### Dominio implementado

El esquema estricto está en `convex/schema.ts`:

- identidad: organizaciones, sedes, personas, identificadores, relaciones y membresías;
- seguros: ARS/payers, planes, coberturas y credenciales profesionales;
- catálogo/operación: servicios, recursos, requisitos, calendarios, reglas, excepciones y feriados;
- agenda: series, sesiones, ofertas, reservas, participantes, asignaciones, eventos e idempotencia;
- colas: entradas, contadores, lista de espera y ofertas;
- automatización: principals, API keys, prompts, tools, consentimientos, notificaciones, outbox, webhooks, provisión, onboarding y auditoría.

Tablas heredadas conservadas: `tenants`, `channels`, `aiStates`, `catalogItems`, `knowledgeItems`, `requests`, `requestEvents`, `appointments`, `quotes`, `integrationConnections` y `webhookEvents`.

Se ampliaron validadores heredados para aceptar campos ya existentes sin usar `v.any()`:

- `catalogItems`: moneda, SKU, source, impuesto y unidad opcionales;
- `knowledgeItems`: categoría, prioridad, revisión, estado, tipo, usuario y visibilidad opcionales;
- `quotes`: request/items, referencias Chatwoot, revisiones y vigencia opcionales.

### Invariantes

- UTC interno y zonas IANA; RD usa `America/Santo_Domingo`.
- Ofertas opacas, de un uso y cinco minutos de vigencia.
- `booking.create` revalida capacidad y recursos en una mutación serializable.
- `pending_confirmation` consume capacidad.
- Reprogramación atómica con historial inmutable.
- El turno autoritativo solo nace en check-in.
- Callbacks externos tipados, firmados e idempotentes.
- PII sensible con AES-GCM, índice ciego HMAC y máscara para UI.

Cron jobs: outbox cada minuto, liberación segura cada cinco minutos y revisión de feriados diaria a las 12:00 UTC.

### API

Contrato: `GET /v1/openapi.json`. Hay endpoints para onboarding/OTP/publicación/provisión, API keys, catálogo, sedes, recursos, personas, seguros, calendarios, clases, disponibilidad, reservas, cola, lista de espera, feriados, callbacks y runtime del agente.

Flujo obligatorio del agente:

1. `catalog.search`, máximo cinco resultados.
2. `availability.summarize`.
3. `availability.listOptions`, máximo cinco opciones verificadas.
4. `booking.create` con `offerId` e `Idempotency-Key`.

### Configuración n8n

Crear como Variable visible de n8n:

```text
REQUEST_ENGINE_CONVEX_SITE_URL=https://zealous-turtle-311.convex.site
```

Los HMAC no deben ser Variables normales. Para el MVP se cargan como secretos del servicio n8n:

```text
REQUEST_ENGINE_INTEGRATION_WEBHOOK_SECRET=<igual a Convex>
N8N_OTP_WEBHOOK_SECRET=<igual a Convex>
N8N_OUTBOX_WEBHOOK_SECRET=<igual a Convex>
```

Configuración del runtime n8n, seguida de reinicio:

```text
NODE_FUNCTION_ALLOW_BUILTIN=crypto
N8N_BLOCK_ENV_ACCESS_IN_NODE=false
```

Para producción conviene un nodo privado con Credential propia o External Secrets. Las Variables de n8n no son una bóveda de secretos.
