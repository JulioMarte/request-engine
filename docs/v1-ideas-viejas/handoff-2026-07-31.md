## 1. Objetivo vigente en V1

Request Engine era un motor multiempresa de agenda operado por agentes de IA y por un panel humano. Convex era la fuente de verdad transaccional; Chatwoot conservaba conversaciones y handoff; Evolution API proporcionaba WhatsApp Baileys solo para pilotos; n8n era el orquestador temporal.

El MVP cubría citas con hora (`fixed_time`), ventanas por orden de llegada (`arrival_window`), clases recurrentes (`class_session`), sedes, recursos, horarios, excepciones, feriados, reservas grupales, tutores, seguros, exequátur, confirmaciones, lista de espera, onboarding conversacional, REST/OpenAPI y panel administrativo.

Fuera de alcance entonces: pagos, reclamaciones ARS, expediente clínico, inventario, logística y calendarios externos funcionales.

### Dominio implementado

El esquema estricto estaba en `convex/schema.ts`:

- identidad: organizaciones, sedes, personas, identificadores, relaciones y membresías;
- seguros: ARS/payers, planes, coberturas y credenciales profesionales;
- catálogo/operación: servicios, recursos, requisitos, calendarios, reglas, excepciones y feriados;
- agenda: series, sesiones, ofertas, reservas, participantes, asignaciones, eventos e idempotencia;
- colas: entradas, contadores, lista de espera y ofertas;
- automatización: principals, API keys, prompts, tools, consentimientos, notificaciones, outbox, webhooks, provisión, onboarding y auditoría.

Tablas heredadas conservadas: `tenants`, `channels`, `aiStates`, `catalogItems`, `knowledgeItems`, `requests`, `requestEvents`, `appointments`, `quotes`, `integrationConnections` y `webhookEvents`.

Se ampliaron validadores heredados para aceptar campos ya existentes sin usar `v.any()`:

- `catalogItems`: moneda, SKU, source, impuesto y unidad opcionales;
- `knowledgeItems`: categoría, prioridad, revisión, estado, tipo, usuario y visibilidad opcionales;
- `quotes`: request/items, referencias Chatwoot, revisiones y vigencia opcionales.

### Invariantes V1

- UTC interno y zonas IANA; RD usa `America/Santo_Domingo`.
- Ofertas opacas, de un uso y cinco minutos de vigencia.
- `booking.create` revalida capacidad y recursos en una mutación serializable.
- `pending_confirmation` consume capacidad.
- Reprogramación atómica con historial inmutable.
- El turno autoritativo solo nace en check-in.
- Callbacks externos tipados, firmados e idempotentes.
- PII sensible con AES-GCM, índice ciego HMAC y máscara para UI.

Cron jobs históricos: outbox cada minuto, liberación segura cada cinco minutos y revisión de feriados diaria a las 12:00 UTC.

### API V1

Contrato: `GET /v1/openapi.json`. Había endpoints para onboarding/OTP/publicación/provisión, API keys, catálogo, sedes, recursos, personas, seguros, calendarios, clases, disponibilidad, reservas, cola, lista de espera, feriados, callbacks y runtime del agente.

Flujo obligatorio del agente V1:

1. `catalog.search`, máximo cinco resultados.
2. `availability.summarize`.
3. `availability.listOptions`, máximo cinco opciones verificadas.
4. `booking.create` con `offerId` e `Idempotency-Key`.

### OTP

Validaba Bearer/payload, reintentaba tres veces y respondía `202`.

### Evolution Events

Usaba ruta opaca, filtraba QR/conexión, normalizaba, firmaba `timestamp.body` y llamaba a Convex.

### Outbox Router

Verificaba HMAC y envelope versionado. Su safety gate fallaba deliberadamente hasta conectar destinatarios/handlers porque un `2xx` prematuro podía hacer que Convex marcase un evento como entregado.

### Chatwoot Agent Gateway

Aceptaba sólo eventos entrantes adecuados y evitaba loops. Su safety gate impedía activarlo hasta emitir API key organizacional y conectar tools deterministas.
